# Audit guide

## 1. Scope

| File | nSLOC | What it is |
|---|---|---|
| [`src/DarkVaultCore.sol`](src/DarkVaultCore.sol) | 218 | The vault's account paths: state, constructor, `deposit`, `applyPending`, `transfer`, `withdraw`, the proof public inputs and the checks they call |

Counted on `forge fmt` output with `npx solidity-code-metrics src/DarkVaultCore.sol` (the nSLOC
column; cloc counts 236 code lines).

`DarkVaultCore` is the part of the deployed vault that holds and moves funds. `src/DarkVault.sol`
inherits it and adds the owner and guardian functions and the views; together they compile to the
runtime code deployed at `0xeD7a0c6899a6AC94Aea7A5b2F8f24a948042DA9C` on Robinhood Chain (4663),
byte for byte apart from the metadata hash. `python3 script/verify-mainnet.py` checks that against
the chain (section 3).

The six files in `lib/dark-contracts` are verbatim copies of the same paths under `contracts/src` in
DarkWalletRH/dark-contracts v1.0.4 (commit `1ffe0d46c38603b612b165c54de403a5002a0fa6`): every file
there except `DarkVault.sol`, which `src/` replaces. `bash script/verify-lib.sh` checks each one
against that tag.

## 3. Tying this code to the chain

```bash
npm ci
forge build
python3 script/verify-mainnet.py
```

The script fetches the runtime code at the vault address (from `$RPC_URL` if set, else the public
Robinhood RPC, falling back to Dark's own `api.darkwallet.cash` RPC; the output names the one used)
and requires it to equal the `DarkVault` build here, byte for byte, after zeroing the four
immutables and ignoring the trailing metadata. It then checks the immutables against
`deployments/4663.json`, both as stored in the code and role by role through the vault's own
`usdg()`, `registry()`, `transferVerifier()` and `withdrawVerifier()` getters. The
compiler settings are in `foundry.toml` (solc 0.8.28, `via_ir`, 1,000 optimizer runs, cancun).

## 4. Where we would like you to look hardest

1. **Proof ↔ public-input binding.** `_transferInputs` (21 inputs) and `_withdrawInputs` (12) must
   pass each input in the order and encoding the circuit expects, with the value the contract
   means: chain id, vault, `msg.sender`, `to`, nonce, registry keys, the stored `available`
   ciphertext, and the transfer limits. The order is defined in `circuits/public_inputs.toml` in
   dark-contracts. Look for replay across chains, vaults, accounts, recipients or nonces, and for
   caller-controlled inputs the proof does not pin.
2. **Ciphertext accounting and solvency.** `mulG` in `deposit` and `withdraw`, the transfer's
   subtraction from the sender and addition to the recipient's pending balance, and the `tvl` and
   `netInflow` bookkeeping. Can any sequence of calls make the encrypted balances exceed the USDG
   the vault holds, or make a `withdraw` revert for an honest account?
3. **Pending transfers.** The pending/available split against front-running, `applyPending`'s
   lower-bound count (`PendingChanged`), dust griefing, and `aeBalance` handling.
4. **Token handling and reentrancy.** The balance-delta check in `deposit`, checks-effects-
   interactions in `withdraw`, and `nonReentrant` across the four account functions.
5. **Limits and pause.** Nothing may block `withdraw` or `applyPending`; `deposit` and `transfer`
   must enforce every limit; `_checkCeilings` must hold for the constructor's limits.

## 5. Known issues and accepted risks

1. **Chain operator.** Robinhood Chain's centralized sequencer can filter any transaction, `withdraw`
   included, and the chain can be upgraded with no delay. "Exit is never blocked" holds against
   Dark's roles, not against the chain operator.
2. **USDG.** The issuer may be able to freeze the vault's address, and USDG is an upgradeable
   EIP-1967 proxy. `deposit`'s balance-delta guard sees only its own `safeTransferFrom` and
   `withdraw` has none; a fee taken from the vault on top of a withdrawn amount, or a balance change
   between transactions, would leave `balanceOf(vault) < tvl` with no on-chain signal until the last
   withdrawals revert.
3. **The generated verifier.** We know of no public audit of Barretenberg's Honk Solidity verifier
   template; the vault treats `verify` as an oracle.
4. **`InvalidProof` is unreachable on chain.** The deployed verifiers revert on a bad proof with
   their own error instead of returning `false`; only the test verifier returns `false`.
5. **Public-input arrays are written out by hand.** Unit tests pin each array against a copy in
   the test, and real proofs have passed through the vault on testnet and mainnet, but no test in
   this repository drives a real proof through it.
6. **`withdraw` emits `Withdrawn` before the token transfer.** Checks-effects-interactions still
   holds.
7. **Limit consistency is not checked on chain.** The constructor and `setCaps` check only the hard
   ceilings and `minTransfer >= 1`: not `minDeposit <= maxDeposit`, `minTransfer <= maxTransfer`,
   per-transaction caps <= `maxAccountInflow` <= `tvlCap`, or `minDeposit >= 1` (with
   `minDeposit = 0`, `deposit(0)` is a nonce-bumping no-op). `setCaps` changes go through the
   48-hour timelock and are public before they apply. `tightenCaps` checks none of this and applies
   instantly; a minimum above its maximum disables `deposit` or `transfer`, never `withdraw` or
   `applyPending`.
8. **Cap-check gap in the tests.** The code is correct, but five deletions leave all 60 tests
   passing: the `maxAccountInflow` or `maxTransfer` ceiling in `_checkCeilings`, and the
   `maxAccountInflow`, `maxTransfer` or `tvlCap` comparison in `tightenCaps`. Such a regression
   would let the 1-of-2 guardian raise a cap instantly.
9. **Fixed fuzz seed.** The curve library's differential test runs the same 500 cases each run
   (forge keeps `block.timestamp` fixed).
10. **Verifier identity rests on the deployment record.** The constructor checks only that the two
    verifiers differ and have code, and that the registry has code; which verifier is which is
    established by dark-contracts' pin checks and by `script/verify-mainnet.py`.
11. **Governance is a deploy-time property.** Nothing on chain requires the owner to be a timelock:
    after a `transferOwnership` has passed the 48-hour delay and been accepted, the new owner acts
    with no delay (within the ceilings, with no path to USDG). `setGuardian` takes any non-zero
    address. The guardian Safe (1-of-2) has two signers who are also two of the owner Safe's three.
